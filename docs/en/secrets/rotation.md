# Secrets: key hierarchy & rotation runbook (T3.3 + lifecycle verbs)

> English mirror of [docs/secrets/rotation.md](../../secrets/rotation.md) — the Chinese original is the canonical source; this plane is asserted at file-existence level by the docs-ssot en-parity battery.

> Design-principle mapping: clear boundaries (the two user/srv domains) ·
> lifecycle (rotation is the norm, not incident response) · least privilege
> (one key opens only one class of gate) · state machine
> (EMPTY → USER_ONLY → USER+HOST).
>
> Operational-plane entry points: `just secrets-guide` (lifecycle map) · `just secrets-status` (current-state audit).

## 1. Layered model (landed in this repository)

```
keys:
  &user_<name>  age1…            # 个人域: 登录密码 / github token
  &host_<alias> age1…            # 基础设施域: 只存在于 host 机器上

creation_rules:
  secrets/**/core/base/(user|nix)/**   → [ user_<name> ]               # 单 key
  secrets/**/core/srv/**               → [ host_<alias>, user_<name> ]  # 双 key
```

- **user domain** (`core/base/{user,nix}`): only the user key can decrypt. Leak blast radius = personal identity.
- **srv domain** (`core/srv/`, the five db passwords): either the host key or the user key
  decrypts (key group semantics = any single one suffices; upgrading to a k-of-n
  threshold only requires adding more keys to a single group — likewise for sops's
  `shamir_threshold`).
- **Blast radius**: user-key compromise ≠ total compromise — the db passwords can be
  rotated into a new policy containing only the host key; host compromise does not
  affect the user domain (a host has no decryption need for user-domain files).
- **Dual key on the local machine (own host)**: when a personal machine also runs srv
  services (the dev-on-demand db profile) it consumes both domains at once — the user
  key decrypts the user domain, the host key decrypts the srv domain (after hardening).
  The age identity file natively holds multiple identities; `key-install-host` merges
  the host identity into the local `~/.config/sops/age/keys.txt` (sops-nix's `keyFile`
  already points there — the CLI and activation share the same identity set).
- **Distribution layer**: recipients are decided by the path_regex of `creation_rules`
  (the first matching rule takes effect — the same semantics as sops itself). The
  toolchain executes the rules purely as data — `secrets-rotate.sh` parses them into
  IR and matches in order, with zero domain knowledge hardcoded; the keys: aliases
  carry a domain payload (`user_*` / `host_*` prefixes), the same idiom as the `.tag`
  payload rows of the nix-types enums.

## 2. Lifecycle state machine & bootstrap

```
EMPTY ──just secrets-init──▶ USER_ONLY ──just key-add-host──▶ USER+HOST
EMPTY ──just secrets-init <alias> <age1…>──▶ USER+HOST   （直达双 key）
USER+HOST ──just key-remove──▶ USER_ONLY （随后 secrets-sync 重加密）
```

**EMPTY is the repository's factory state** (what a fresh clone sees): `.sops.yaml`
and all ciphertext blobs **do not exist** — they are generated by the just workflows
(`secrets-init` / `secret-set`) and enter the repository only after being encrypted
with **your own** age key. No key material generated by a tool or by anyone else can
bootstrap for you (without your private key there is no way to re-encrypt) — this is
precisely why this repository ships no pre-provisioned keys. Eval is lenient toward
the EMPTY state (`lib/shared/lang/validate.nix` only traces a hint with the bootstrap
command; once a single blob appears on the tree, declared-but-missing is an error).

The template (`docs/tmpl/sops/sops-rules.yaml.tmpl`) carries a **dual rendering
mode**: the user key row renders unconditionally, while the host key row (marked
`# __HOST__`) is decided by the bootstrap invocation —

| Bootstrap invocation | Rendering result | Landing state |
| --- | --- | --- |
| `just secrets-init` | host rows stripped (sed `/__HOST/d`) | USER_ONLY |
| `just secrets-init <alias> <age1…>` | host rows substituted in (keys + srv domain) | USER+HOST |

After bootstrap, `.sops.yaml` is the policy truth — `rules-init` refuses to overwrite
a file that has already evolved (only `rules-reset` resets it, preventing the
two-domain hierarchy from being knocked back to a single key).

**New personal-machine bootstrap** (brand-new machine, three commands):

```console
just init <username>        # shared.nix → hardware.nix → sops 基线
just secret-set-all         # 交互式录入全部秘密（输入即加密）
just nixos-switch nixos     # 或手工 nixos-rebuild —— 落地
```

**Server day-one direct bootstrap** (host key material first, two steps replacing three):

```console
just key-new-host <alias>          # ① 生成 keypair（仓外交付副本）
just init <username> <alias> age1… # ② 直达 USER+HOST（srv 域双收件人）
# ③ host-<alias>.age → 目标机 /var/lib/sops-nix/key.txt（chmod 400）
#    （keyFile 落点现状见下方注记）+ shred
```

**own host = srv host (the personal machine's dual key landing locally, five steps)**:

A personal machine (mounting db services via dev-on-demand) is simultaneously a
consumer of the user domain and the srv domain. In the baseline state (the srv group
containing the user key) a single user key decrypts everything; but both design paths
require the host identity to land on this machine at the same time: under the
**hardening policy** (rotating the srv recipients to host-only — directly edit the
srv key group in `.sops.yaml` to remove the `*user_*` references, then
`secrets-sync`) this machine, holding only the user key, will be unable to decrypt the
srv blobs — activation fails outright; the **independent recovery path** (if the
user key is compromised or lost on another machine, this machine's host identity
remains a valid decryptor of the srv domain — key group OR semantics). Merge rather
than build separate infrastructure:

```console
just key-new-host <alias>           # ① 生成 keypair（仓外交付副本）
just key-add-host <alias> age1…     # ② 公钥接线（或 init 直达双 key）
just secrets-sync                   # ③ 存量 blob 迁移
just key-install-host <alias>       # ④ identity 合并进本机 sops key 文件
shred -u ~/Downloads/host-<alias>.age  # ⑤ 本机已持有，销毁交付副本
```

`key-install-host` is idempotent per secret-key row (re-installs are skipped),
appends atomically (mktemp + cat + mv — the key file is never truncated midway),
preserves chmod 400, and, once installed, prints every identity public key on this
machine (`age-keygen -y` lists multi-identity files line by line). The local
identities section of `just secrets-status` audits what this machine holds at any
time.

**New srv host bootstrap** (incremental onboarding after a USER_ONLY bootstrap, four steps — see `just secrets-guide`):

```console
just key-new-host <alias>           # ① 生成 keypair（仓外交付副本）
just key-add-host <alias> age1…     # ② 公钥接线进 .sops.yaml（srv 域）
just secrets-sync                   # ③ sops updatekeys ×N（存量 blob 迁移）
# ④ host-<alias>.age → 目标机 /var/lib/sops-nix/key.txt（chmod 400）
#    然后 shred 交付副本
```

> Current state of the keyFile landing spot: the module side
> (`platform/nixos/system/core/sec/secret/default.nix`) currently pins
> `sops.age.keyFile` to the user's home directory
> `~/.config/sops/age/keys.txt` (`generateKey = true`, the own-host form).
> `/var/lib/sops-nix/key.txt` is the target position for the headless
> (no-home-directory) server form — to be parameterized when the second server
> machine lands (same origin as known-boundaries ledger item #5 in the README).
> Before delivery, the target machine's actual keyFile configuration is
> authoritative.

**Three-layer declaration of a new secret** (the configuration layer is the truth; scripts merely execute):

1. `shared.nix.tmpl` declares the dotted key → `just shared-generate <username>`
2. the `docs/tmpl/sops/<rel-path>.yaml` template (leaf key = the last path segment;
   placeholders `__SECRET_VALUE__` + `__USERNAME__`)
3. the registry `secrets/registry.toml` (DATA, committed with the repository) gains a
   line `alias = { key, rel, prompt, transform }` — written in full by the single
   command `just secrets-add <alias> <rel-path> [prompt] [transform]`
   (the shell-side `secrets-db.py` takes care of landing all three places in sync;
   after hand-editing the toml, run `just secrets-db-sync` to refresh the cache)

The registry is the only alias→secret mapping: `secret-set/get/edit/remove` and
`secrets-list` are all thin traversals over it — adding a new secret requires
**zero new recipes**. `_secrets-registry` is merely an internal forwarding recipe
(rendering the toml into pipeline rows for the script to consume), not a
registration entry point; registering / retiring / editing prompt text always goes
through `secrets-add` / `secrets-remove` / `secrets-edit`.

## 4. Operational plane: the full just verb table (create / update / destroy × key / rules / blob)

| Verb | Object | just command | Notes |
| --- | --- | --- | --- |
| create | key (user) | `secrets-init` | idempotently generates ~/.config/sops/age/keys.txt |
| create | key (host) | `key-new-host <alias>` | out-of-repo delivery copy + chmod 400 + wiring instructions |
| create | key (host→local) | `key-install-host <alias>` | own-host dual key: identity merged into the local sops key file (idempotent / atomic / preserves 400) |
| create | rules | `secrets-init` | user-only baseline (skipped if already present) |
| create | registry | `secrets-add <alias> <rel>` | all three layers written in one go (declaration + template skeleton + registry.toml row) |
| update | registry | `secrets-edit <alias> [prompt] [transform]` | edits the registry row (prompt text / transform) |
| audit | registry | `secrets-show` / `secrets-declared` / `secrets-db` | full dossier for a single entry / declaration↔registry drift / cache state |
| destroy | registry | `secrets-remove <alias>` | retires the registry row (refuses while ciphertext still exists) |
| create | blob | `secret-set <alias>` | interactive entry (upsert semantics — overwriting is updating) |
| update | key (user) | `key-rotate-user age1…` | guided three steps (replace → sync → accept historical exposure) |
| update | key (host) | `key-rotate-host age1…` | guided five steps (0/4 pick the old alias first; add before removing — no bare window) |
| update | rules | `key-add-host` / `key-remove` | incremental evolution (template not regenerated) |
| update | blob | `secret-set <alias>` | re-encrypt (same as create, overwrite) |
| update | blob (all) | `secrets-sync` | sops updatekeys full re-encryption |
| audit | all | `secrets-status` / `secrets-verify` / `secrets-list` | keys/rules/blob overview + consistency + alias table |
| destroy | key (user) | `key-destroy` | irreversible |
| destroy | key (host) | `shred -u <delivery-copy>` | delivery copy destroyed (the target machine is the sole holder) |
| destroy | rules | `rules-destroy` (+`key-remove`) | delete all / incremental removal |
| destroy | blob (one) | `secret-remove <alias>` | single file (warns that the configuration-layer declaration is handled separately) |
| destroy | blob (all) | `secrets-destroy-all` | all sops assets (including rules and key files) |

The rotation modes map one-to-one onto `scripts/sh/secrets-rotate.sh`:

| Mode | Effect | When |
| --- | --- | --- |
| `check` (`just secrets-verify`) | verifies each blob's metadata recipients == the `.sops.yaml` rules | CI / daily |
| `update` (`just secrets-sync`) | `sops updatekeys` full re-encrypt to the current rules | hierarchy migration, adding a key |
| `rotate user age1…` (`just key-rotate-user`) | generates the three-step guide (replace key → sync → historical-exposure decision) | scheduled / suspected compromise |
| `rotate host age1…` (`just key-rotate-host`) | generates the five-step guide (pick old → add → sync → remove old → sync) | scheduled / suspected compromise |

`check` is lenient toward the EMPTY factory state (no rules, no blobs → notify and
pass); **blobs existing without a `.sops.yaml` is the only fatal form** (the
distribution layer has vanished while ciphertext remains — plaintext-risk level).

**Compromise response** (worst case):

1. Revoke: `just key-remove <alias>` → `just secrets-sync` re-encrypt (the
   compromised key can never decrypt new blobs again).
2. Thanks to sops's metadata MAC, the old key's holder cannot forge new blobs.
3. Run `ALTER USER … PASSWORD` once more on the database side (a configuration-layer
   rotation does not replace a data-layer rotation).

### Plaintext → ciphertext → runtime (the six-phase pipeline from the runbook's view)

The mechanisms view (the seven-layer pipeline panorama, the permission matrix table,
the data-driven derivation rules) is in
[mechanisms.md §5](../architecture/mechanisms.md); this section covers only the
three phases the operator touches:

- **PLAIN (`secrets/plan/**`, local reference, never commit)**: `secrets-plan-create`
  generates plaintext instance skeletons — they are the "answer key" of the bootstrap
  period (a glance at what structure a given secret should have), not the working
  norm: entry always goes through `secret-set` (interactive read → transform
  [plain / mkpasswd sha-512 -R 5000] → template substitution [awk ENVIRON for
  injection safety] → sops encrypt → atomic mv of the temp file into
  `secrets/chipr/`); plaintext never sits on disk waiting. The whole
  `secrets/plan/` directory is in `.gitignore`.
- **CIPHER (`secrets/chipr/**`, committed with the repository)**: the output of
  `secret-set`; `secrets-verify` checks recipient consistency, `secrets-sync`
  re-encrypts everything.
- **RUNTIME (activation moment)**: sops-nix decrypts and places at activation per
  the declarations — the secret with `neededForUsers = true` (currently only
  `user.password`) lands in `/run/secrets-for-users/` (available **before** user
  creation — passwords must hit exactly this window); the rest land in
  `/run/secrets/`, each secret getting owner/mode permissions (the complete
  mode/owner/group matrix of the 7 secrets is in mechanisms.md §5). Services consume
  via `config.sops.secrets.<name>.path` (a path reference, no copy). Acceptance:
  after activation, check `ls -l /run/secrets/` against the matrix item by item.

## 5. CI gate (`.github/workflows/ci.yml` → security stage)

- Set the repository secret `AGE_SECRET_KEY` (the age private key,
  `AGE-SECRET-KEY-1…` form; injected inside the workflow as env `SOPS_AGE_KEY` —
  sops only recognizes the latter).
- Stage behavior: `sops -d --output /dev/null` on each `secrets/**/*.yaml` in turn;
  any decryption failure = red. When the secret is not configured the stage is
  skipped (neither silently succeeding nor blocking).
- **key hierarchy check (new)**: the `scripts/sh/secrets-rotate.sh check` step —
  ① every secret file must be covered by some creation_rule (NO-RULE = plaintext
  risk) ② blob recipients == the rule's key group (DRIFT = rules changed without
  re-encrypting). Complementary to the decryption gate: the decryption gate verifies
  *decryptability*, check verifies *recipient consistency*.
- **Leniency for the EMPTY factory state**: before bootstrap (no `.sops.yaml`, no
  blobs) each verification step prints a notice and passes — EMPTY is a legal entry
  state, not a failure state; after bootstrap it automatically turns strict.

## 6. Why bootstrap is left to the holder

An honest record (plan-vs-reality correction): the precondition for a script to
encrypt/re-encrypt is holding **your private key**. The deliverer of this repository
is the holder themself — any rewriting of ciphertext without the holder's knowledge
amounts to key compromise. The boundary of this repository is therefore: **lay out
the layered rule templates, the lifecycle tooling, the CI gates, and the
documentation in full, so that both bootstrap and rotation become one command for
the holder** (`just init` / `just secret-set-all` / `just secrets-guide`).
